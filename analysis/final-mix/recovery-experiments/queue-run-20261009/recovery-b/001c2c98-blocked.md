# 001c2c98: store scheduling and register allocation blocker

Complete live layout is 76 bytes. The best original archived source matches all instructions except the last two stores at offsets 0x38 and 0x3c: it stores flags before the vtable address, while the original stores the vtable address first. The original return-address restore at offset 0x24 is already correct.

Eleven fresh isolated variants were probed under the pinned compiler. Marking either final store volatile individually leaves the original two-word mismatch unchanged. Marking both volatile changes earlier load and register scheduling. Marking all three stores volatile fixes final semantic store order and preserves the original early return-address restore, but changes state and flags register allocation and other scheduling. A memory barrier between final stores also alters earlier registers and delays the return-address restore. Precise assembly memory outputs and fixed-register variants did not produce equality. Complete source/proof files are retained; 001c2c98-blocked-evidence.json binds each proof and original range hash.

Next hypothesis: use the successful all-store-volatile variant as a starting point, but constrain the order and allocation of the state load/OR chain separately from the flags chain. Identify an alias-aware expression or exact memory operand dependency that keeps the original t5 state, t6 flags and t7 constants without inserting a global memory barrier. Current trials do not establish compiler impossibility. Do not repeat blanket memory barriers or individual final-store volatile toggles.
