# 00265740 blocked (queue prologue-save-order)

Target: 00265740, 60 bytes, attempts 2 -> 6 versions probed by orch1-pro02.

Residual: prologue store order. Original `sd ra,8(sp); sd s0,0(sp)`. Best bodies (v1/v2/v5) compile
the body exactly but emit `sd s0,0(sp)` before `sd ra,8(sp)`. Frame 16, offsets s0@0 / ra@8 always correct.

Evidence:
- v1 baseline (barriers, `func_00139d78(object)`): body exact, 2 words, s0-first.
- v2 `register u32 object asm("$16")`: no effect.
- v3 `asm volatile("" : "+r"(object))`, no barriers: 3 words, loses `move a0,v0` -> `move a0,s0`.
  The memory barriers are what keep the argument copy in v0; do not remove them blindly.
- v4 no barrier, helper result kept live in v0 (`s32 got=...; object=(u32)got; func_00139d78((u32)got)`):
  prologue order becomes CORRECT (ra first) and the body matches instruction for instruction, but
  `sd s0,0(sp)` is scheduled into the `jal` delay slot, so the block is 56 bytes (13 differing words).
- v5 v4 plus `asm volatile("" ::: "memory")` before the first call: back to 60 bytes, s0-first again.
  Any memory barrier anywhere in the function restores the s0-first order.

Hypothesis for the next attempt: keep the barrier-free v4 shape (that is what yields ra-first) and
stop the `sd s0,0(sp)` from being scheduled into the first `jal` delay slot -- e.g. with a
pre-call instruction-neutral asm tied to s0 (`asm volatile("" : "+r"(object));` placed before the
first call rather than after it, or an operand marker on the live v0 result) instead of a
memory-clobber barrier, which is what reverts the order.
