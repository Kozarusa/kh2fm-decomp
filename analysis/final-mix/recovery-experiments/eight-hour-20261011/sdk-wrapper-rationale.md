# SDK wrapper and build-boundary rationale

The accepted SDK wrapper families forward operation identifiers and Word payloads through a shared low-level gateway. Repeated instruction patterns were used to locate candidates, but every accepted wrapper has its own isolated source proof and independent curated-source reprobe. Similarity alone was never accepted as proof.

The original wrappers explicitly establish and restore a frame pointer. The recovered sources express payload layout and gateway calls in C++ and use narrow ABI primitives for that frame transport where the pinned compiler would otherwise choose a different frame. Some wrappers also require constant transport, outgoing stack arguments, or a precise GP-relative global load. These primitives preserve observed machine behavior; they are not wholesale pasted assembly function bodies. The queue-nu-prime-constraint-rationale document explains later floating conversion and variable Word shift primitives.

A full-build failure in queuekappaprime exposed a linker input-section alignment issue: an eight-byte-aligned C++ function intended for a native address congruent to four modulo eight was placed four bytes late, changing a caller's jump relocation. The repair reduces only the validated executable function section's alignment metadata to four. Instructions, relocations, compiler flags, and accepted caller source remain unchanged. The failed executable, object diagnostic, helper backup, hashes, and successful retry are preserved. This repair subsequently passed the cumulative 126-bundle matrix.

The build helper now also rejects a C++ function linked at an address different from its native registry address. Existing assembly normalization has its own intentional temporary placements, so the new guard applies to C++ inputs. Negative controls and the initial overly broad guard failure were preserved; the scoped version passed the 127-bundle matrix and later cumulative acceptance runs.

These results establish instruction equality for registered native ranges under the pinned compiler and linker. They do not establish original source names, class layouts, high-level behavior on other platforms, or a complete source-only game build. Remaining fallback ranges still come from original executable bytes.
